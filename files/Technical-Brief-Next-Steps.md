# Technical Brief — AI Visibility Studio & the Surfaced Engine
*Prepared June 10, 2026 · companion to `ai_visibility_studio.py` and the Surfaced codebase*

## Where things stand

The shipped tool, `ai_visibility_studio.py`, is a single-file, zero-dependency Python application. It runs a local web server, accepts any URL, fetches the page exactly the way a non-JavaScript crawler does, and produces two scores. GEO (Generative Engine Optimization) measures whether AI systems can access, read and trust the page: it checks robots.txt permissions for the six citation crawlers (OAI-SearchBot, ChatGPT-User, Claude-SearchBot, Claude-User, PerplexityBot, Perplexity-User) separately from the training-only crawlers, then evaluates HTTPS, raw-HTML word count, text-to-code ratio, authorship, dates, outbound references, title, meta description and canonical URL. AEO (Answer Engine Optimization) measures whether the content is shaped like answers: heading hierarchy, lists and tables, question-style headings, FAQ presence, JSON-LD structured data depth, quotable 30–70-word answer paragraphs, and image alt coverage. Every failed check carries a plain-English fix and an impact rating, and the renderer emits a fully self-contained HTML report saved to `reports/`.

Architecturally the file is seven small modules in one script: crawler identity constants, a fetcher (urllib with gzip and redirect handling), a hand-rolled robots.txt group parser, an HTMLParser subclass that extracts everything in a single pass, a scoring layer that converts observations into weighted `Check` objects, a report renderer, and a threaded HTTP server. This deliberately mirrors the Surfaced codebase conventions: standard library core, no required third-party dependencies, and clean seams so each module can later be lifted into the Surfaced packages.

## Known limitations to be honest about

The tool sees what a non-JS crawler sees, which is the right default but means client-rendered sites score near zero even when the *rendered* page is fine; the SPA heuristic (low word count plus `id="root"`/`id="app"` plus heavy script counts) flags this but cannot quantify it. The robots.txt parser handles the common grammar (agent groups, blanket disallows, allow overrides) but not full path-pattern precedence with wildcards. Scores are a proxy: they predict citability, they do not measure it. And single-page analysis can misjudge a site whose trust signals live on other pages (an About page, an author hub). Each limitation maps to a next step below.

## Next steps, in priority order

**Step 1 — Multi-page site audits.** Move from page scoring to site scoring. Discover URLs from `sitemap.xml` (falling back to a breadth-first crawl of internal links, capped at 25–50 pages with a politeness delay of about one second per request), score each page with the existing engine, then roll up: site-level Access and Identity checks run once, while Content, Trust and Answer-shape pillars aggregate as weighted averages with the worst offenders surfaced. The data model change is small: introduce a `SiteResult` that holds a list of page `Result` objects plus rollup scores, and extend the report with a per-page table. This is the highest-leverage step because real clients ask about sites, not pages.

**Step 2 — Render-gap measurement.** Replace the SPA guess with a measurement. Add an optional mode that loads each page in headless Chromium via Playwright (`pip install playwright; playwright install chromium`), extracts the rendered text, and computes a render gap: `1 − (raw_html_words / rendered_words)`. A gap above roughly 40% becomes a high-priority finding with concrete numbers ("crawlers see 210 of your 1,840 words"). Keep this behind a flag so the core tool stays zero-dependency; the architecture seam is a second `fetch_rendered()` implementation feeding the same parser.

**Step 3 — Live mention-rate tracking (this is Surfaced ticket T-2/T-3 territory).** On-page scores are the proxy; mention rate is the product. Build the probe pipeline: maintain 20–40 seed questions per client vertical (the questions real buyers ask an assistant), run them on a schedule against the Anthropic and OpenAI APIs with web search enabled, then parse responses for brand mentions, competitor mentions, sentiment, and citation URLs. The metrics that matter are mention rate (share of probes mentioning the brand), share of voice (brand mentions over total category mentions), and citation rate (probes where the brand's own domain is cited as a source). Persist every probe run with model, date and full response so trends are auditable. Track token spend per probe run as COGS from day one, exactly as `CLAUDE.md` specifies. Note the existing Surfaced scaffold already has the probe runner, parser and connectors — the work here is real seed prompts for the chosen beachhead vertical and a scheduler, which means locking the actual vertical is now a blocking decision, not a nice-to-have.

**Step 4 — History and trends.** Add a SQLite store (`scores.db`, standard library `sqlite3`) recording every audit: URL, timestamp, pillar scores, and check-level results. The report gains a trend sparkline and a "what changed since last run" diff, which is what turns a one-off diagnostic into a recurring habit — and a subscription.

**Step 5 — Attribution.** Close the loop by detecting AI-referred traffic on the client side: referrers from `chatgpt.com`, `perplexity.ai`, `gemini.google.com` and `claude.ai`, plus the `utm_source` parameters assistants increasingly append. Practically this is a small analytics integration (GA4 channel definitions or a lightweight first-party snippet) whose output joins the probe data: "we improved your FAQ schema in March, mention rate rose from 12% to 31% in April, AI-referred sessions doubled in May." That sentence is the entire business.

**Step 6 — Scoring calibration.** Once steps 3 and 5 produce ground truth, treat the pillar weights as hypotheses. Correlate check outcomes with actual citation outcomes across the client base and adjust weights accordingly (a simple logistic regression over check pass/fail features against "was cited" labels is enough at first). This converts the scorer from opinion to evidence and becomes a defensible moat.

**Smaller items worth folding in along the way:** check for an `llms.txt` file and award identity points for it; verify `sitemap.xml` exists and is referenced from robots.txt; flag pages whose last-modified signals are older than 12 months; and add per-engine robots guidance since some sites want to allow citation bots while blocking training bots — the report already separates the two classes, so the fix text can generate the exact robots.txt block to paste.

## Operating guardrails

Respect robots.txt and rate limits in everything the crawler does — a visibility tool that behaves badly toward the sites it audits undermines its own thesis. Keep human review in the loop for any generated content fixes, per the existing `CLAUDE.md` guardrail. And keep the proxy/product distinction visible in every report: on-page score is what we can fix, mention rate is what the client is buying.
